# 整理落地手册（定位、判定与落笔顺序）

`SKILL.md` 给出主工作流；本文把“写到哪里、补什么、如何不破坏已有笔记”的判断压缩成可执行决策。

## 一、定位目标笔记

用户提问后按以下顺序判断，命中即停：

```text
1. 用户明确点名笔记                         → 直接定位该笔记
2. 主题已有同名 / 近名笔记                   → 候选唯一则使用；多个候选请用户选
3. 主题已有 MOC                              → 从阅读路径找最贴合的已有知识单元
4. 以上均没有                                → 进入“新建判定”
```

检索：

```bash
python scripts/vault.py find --query "GPIO"
python scripts/vault.py meta
python scripts/vault.py search --pattern "gpiod" --limit 20
python scripts/vault.py tree
```

### 新建判定

不要一上来就建笔记。先判断新内容与已有笔记的关系：

| 判据 | 动作 |
|---|---|
| 是现有流程的一步、一个概念的补充或一组稳定参数 | 就地补充到对应章节 / 速查区 |
| 能独立完成一个读者任务，且可能被其他笔记引用 | 新建子笔记，并指定 `note_type` |
| 是同主题的自然加深 | 在原笔记“进阶 / 变体”中补充；足够独立再拆分 |
| 横跨两个主题 | 落在更下游的主题；上游笔记添加章节级链接 |
| 只是一次性的项目现场记录 | 先保留在项目记录，不强行包装成通用教程 |

新子笔记默认放在 `<主题目录>/<笔记名>.md`。主题目录没有 MOC 时，只在已积累 3 篇以上可串成路径的子笔记后再建 MOC；不要预先造空架子。

## 二、差距分析：四象限

阅读目标笔记、MOC 与相邻笔记后，把新增内容分入四类：

| 象限 | 特征 | 动作 |
|---|---|---|
| 已有 | 已经讲过，只是表述不同 | 不重复写；补链接、来源或边界 |
| 补台阶 | 新内容依赖前文没有解释的概念 | 在依赖它的章节之前补前置 |
| 顺延 | 已有主线的自然下一步 | 追加到对应章节或“进阶与变体” |
| 跨域 | 属于另一主题或另一读者任务 | 新建 / 追加到正确笔记，并做双向导航 |

### 补台阶的判定

1. 列出新内容首次出现的专业名词、环境状态与隐含工具
2. 逐个检查：在读者第一次需要它之前，是否已经有定义或可达链接
3. 没有则补台阶；台阶本身有新依赖时继续向上补
4. 停在读者已被假定掌握的公共基础；不要把教程膨胀成全部领域历史

落点：

```text
可以塞进“前置条件 / 前置知识”       → 在前面补一小节
属于某个步骤的直接前提               → 放在该步骤之前
超过 60 行且可独立复用               → 拆为独立 explanation / reference 笔记
只影响高级读者                       → 放到“变体与速查”或进阶笔记
```

## 三、先选笔记类型，再选写法

| 新内容的目的 | 类型 | 读者完成后应得到 |
|---|---|---|
| 从零建立完整能力 | `tutorial` | 可运行的最小结果 + 对过程的基本感知 |
| 在既定环境中执行动作 | `how-to` | 一项完成状态 + 明确验证 / 恢复 |
| 理解为什么与何时例外 | `explanation` | 一个可复述心智模型和判断原则 |
| 回忆稳定事实 | `reference` | 快速、准确、带来源的查询入口 |

一篇笔记可有少量辅助内容，但不要让主线在四种写法间无故跳转。完整模板见 `assets/templates/`，详细准则见 `note-style.md`。

## 四、落笔顺序

严格按这个顺序，避免“先堆结论、再补解释”的断层：

1. **先写目标与边界**：读者任务、适用版本、完成标准、已知不覆盖范围
2. **补台阶**：从最必要的基础开始，补到主结论能够自然出现
3. **放主结论 / 最短路径**：教程每步都给可观察预期；解释每条规则都给对照
4. **补机制与速查**：解释为什么、收纳参数和可选分支，不打断主线
5. **补失败信号**：写出最可能遇到的现象、先检查什么、如何恢复
6. **更新导航**：MOC 阅读路径、正文 wikilink、底部“下一步 / 所属主题”
7. **更新事实状态**：`updated`、`status`、必要的 `note_type` / `keywords`
8. **先 dry-run，再正式写入**：检查 diff 后由 `note.py` 自动备份原文件
9. **检查链接与健康报告**：`links`、`audit`、必要时目测 Obsidian 渲染

示例：

```bash
python scripts/note.py insert --file "Linux内核/GPIO 子系统.md" \
  --heading "二、核心概念" --position under \
  --content-file .note-staging/sec.md --renumber --dry-run
```

若 diff 删除行多于新增行，或目录、frontmatter、引用大范围变化，停止写入并重新选择 `insert`、`append` 或拆分策略。

## 五、链接、MOC 与 Bases

完成后检查：

- [ ] 线性学习笔记在主题 MOC 的“阅读路径”里，且顺序反映依赖
- [ ] 同层旁支、参考资料或临时记录不强塞进阅读路径，而是在分支地图 / `related` 中可达
- [ ] 正文首次提到的已有独立概念已加 `[[wikilink]]`
- [ ] 底部明确“下一步、深入理解、所属主题”
- [ ] 新增链接在 `vault.py links` 中可解析

联系类型与处理：

| 联系 | 处理 |
|---|---|
| 上下游依赖 | 两篇底部互挂；在 MOC 中把前置排在后续之前 |
| 同层并列 | MOC 同一分支下放置；互挂“对比” |
| 引用细节 | 正文使用 `[[B#章节]]`，不要重复复制内容 |
| 重复内容 | 不自动合并；双方各留指向，并列入人工复查 |

MOC 管“为什么按这个顺序读”，`.base` 管“按状态 / 类型 / 标签筛选哪些笔记”。出现真实筛选需求后再创建 Base，见 `moc-system.md`。

## 六、待办的出口

| 情况 | 默认处理 |
|---|---|
| 缺证据、需要查源码或复测 | `> [!warning] 待核实` + `status: needs-verify` |
| 尚未解决但没有明确外部行动 | `> [!question] 待办` |
| 有责任人、期限、外部动作和验收标准，且 vault 有任务约定 | 创建 / 更新既有任务系统的任务，并回链笔记 |

不要自动安装任务插件或猜测字段。任务完成后必须回写笔记中的证据和结论。详细边界见 `task-integration.md`。

## 七、汇报模板

```markdown
已整理进 **<仓库>/<笔记路径>**

**读者任务与结构**
- 类型：`tutorial`
- 主线：从 <起始状态> 到 <可观察结果>

**新增 / 补台阶**
- `2.3 <概念>`：补齐 <为何需要它>

**主线与验证**
- `3.1 <动作>`：预期看到 <关键输出 / 生成物>

**联动**
- `<主题> MOC`：阅读路径第 N 位插入本篇
- `[[另一篇#章节]]`：补充了 <关系>

**验证**
- 断链：0 个
- 待核实：<数量或具体项>

**待办**
- <仍需用户确认或外部验证的内容>
```

## 八、常见失败模式

| 症状 | 常见原因 | 处理 |
|---|---|---|
| 主线读不通 | 概念先后倒置，补台阶不够 | 找出首次未定义术语，在使用前补定义或链接 |
| 教程很长但跑不通 | 只有命令，没有预期结果和环境自检 | 逐步补“目标 → 操作 → 预期 → 观察” |
| 笔记像百科条目 | 可选参数、替代方案占据主线 | 将稳定事实移入速查 / reference |
| MOC 退化成标签页 | 阅读路径没有依赖顺序 | 重新排序，旁支移入分支地图 |
| 审计报未进路径 | 参考笔记或历史笔记被一视同仁 | 判断是否应进入路径；否则让它在分支地图可达 |
| diff 大量删除 | 误用 `replace` 或定位范围错 | 只看 dry-run，不落盘，改用 `insert` / 拆分 |
| 待办长期没人看 | 知识缺口与执行任务混在一起 | 用 `audit` 集中复查；必要时按任务约定外化 |
