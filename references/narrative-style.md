# 叙述技法：让台阶读得下去

- **一句话**：循环深入决定**先讲什么**，本篇决定**每一步怎么讲**。前者是骨架，后者是血肉。
- **来源**：分析博客园"海绵寳寳"（cnblogs.com/ljz111）的数据结构系列后提炼。该系列面向新手、阅读量高、几乎每篇十余张配图。
- **适用**：`tutorial` / `explanation`。`reference` 不必照搬（速查要的是密度而非叙述）。

## 一、六条可执行技法

### 1.1 场景先行：先给人、物、数字，再给定义

不写"这是一个求最短路径的算法"，而是先摆一个具体任务。

原例（Dijkstra 篇开头）：

> 战争时期，胜利乡有 7 个村庄 `(A, B, C, D, E, F, G)`，现在有六个邮差，从 G 点出发，需要分别把邮件送到 A, B, C, D, E, F 六个村庄，各个村庄的距离用边线表示（权），比如 A – B 距离 5 公里。
> 问：如何计算出 G 村庄到其它各个村庄的**最短距离**？

**做法**：给出场景时必须包含三样东西——**谁在做、要做什么、约束是什么**。缺一样读者就无法代入。

**判据**：如果删掉场景，直接给定义和规则，读者是否还能理解？能理解说明场景只是装饰；不能理解说明场景承担了实质作用，这是合格的标准。

### 1.2 承认抽象：难的地方要主动说出来

不要假装一段内容很好懂。作者写完规则后直接承认：

> 上面的算法过程脱离了具体的实现，很抽象，下面通过具体一点的实现步骤过程来看看到底是怎么弄的。

开头也留了一句：

> tip：这个算法真的很难讲解，有些地方只能意会了，多思考多看几遍还是可以弄懂的。

**做法**：

- 确实绕的段落，用一句"这段抽象，下面用具体例子展开"过渡
- 允许承认"这里需要多读两遍"——降低读者的自我怀疑，而不是暴露作者的不自信
- 不要每一段都这么说，否则变成口头禅

### 1.3 逐步演算：每轮都给状态快照，标出变化

涉及多轮迭代的机制，不要只给最终结果。作者每轮都列三个数组的完整状态，并用 `↑` 指出本次变动：

```text
    对应的村庄     [A, B, C, D, E, F, G]
         下标     [0, 1, 2, 3, 4, 5, 6]

already_arr     =    [1, 0, 0, 0, 0, 0, 1]
pre_visited_arr =   [6, 0, 0, N, 6, 6, 0]
dis_arr         =   [2, 7, 9, 0, 4, 6, 0]
此次变动的有             ↑  ↑
```

**做法**：

- 每轮一张状态表（表格或代码块，横向对齐）
- 单独一行标出"本次变动"
- 轮数多时，只保留**关键轮次**（第一轮、发生转折的那轮、收敛那轮），中间写"此后重复，直到……"

### 1.4 保留试错：把"想错了"的过程写出来

这是该系列最值得学的点。作者算错了一次，没有偷偷改掉，而是原样写出：

> 这里就出现一个问题：
> 如上图：`GAB = 7`，但是 `GB = 3`，并且在访问 G 点的时候，已经计算出了 `GB` 的距离，所以这里 `GAB > GB` 的，它不应该被更新到这里来。最终调节之后的结果为：

**做法**：

- 给出"第一反应会怎么写"→"哪里不对"→"修正后怎么写"
- 修正后的结果单独再列一次状态
- 不要写成"经过考虑我们选择……"，要写出**具体的错误数值和矛盾**

**为什么有效**：新手卡住的地方往往正是作者卡住的地方。把试错写出来，读者会认领那个错误，然后跟着修正。

### 1.5 代码与输出成对，输出逐条解释

代码块之后紧跟真实输出，然后逐条解释输出的每一部分：

> 从输出结果可以看到：
> - `[true, true, true, true, true, true, true]` 所有节点都访问过了
> - `[6, 6, 0, 5, 6, 6, 100000]` 从起点到达每个节点的前驱节点如数组上所示
>   - G 到 A：前驱就是 G，表示从 G 到达的 A
> - `[2, 3, 9, 10, 4, 6, 0]` 即 `A(2) B(3) C(9) D(10) E(4) F(6) G(0)`

**做法**：

- 代码 → 输出 → 逐项解释，三段紧密相邻
- 解释时把"数值"翻译成"含义"，不要只说"如上所示"
- 输出里不重要的部分直接略过，不要逐字念

### 1.6 换角度验证：证明结论不是巧合

作者算完从 G 出发的结果，又换 C 作为起点重跑一遍：

> 换一个出发点验证
> 验证几个：从 C 到 A 最短路径为 7；从 C 到 B 最短路径为 12（CAB：12、CEGB：15、CAGB：12，虽然有相同的，但是还是最短的）

**做法**：

- 换一个输入、起点、参数或数据规模，重跑同一套流程
- 明确说"这次换 X 验证"，让读者知道这是验证而不是新内容
- 至少验算 2~3 个具体数值，不要只贴一个总输出

## 二、图：什么时候必须画

该系列几乎每篇 10 张以上配图，且**不是为了好看**，每张都承担一个具体职责。

| 图的职责 | 什么时候用 | 形式 |
|---|---|---|
| **状态快照** | 多轮迭代，每轮状态不同 | 同一结构重复画，只改动变化的部分 |
| **并列对比** | 两个方案/两份数据要比较 | 左右并排，中间放箭头并标注"类似的 / 区别在于" |
| **结构分层** | 一个系统有 3~4 层包含关系 | 大框套小框，边缘写层级名与职责 |
| **关系图** | 节点之间有连接与权重 | 节点 + 边 + 边上的数值 |
| **流程时序** | 多方按顺序交互 | 纵向泳道或箭头链 |

**不该画图**的情况：能用一句表格说清的、纯文本罗列、装饰性插图。

> [!warning] 图不能替代文字
> 每张图下面要有 1~2 句说明它体现了什么。读者在手机上可能看不清细节，纯图无文等于没写。

## 三、与"循环深入"的配合

两者是正交的：

```
循环深入（spiral-teaching.md）：概念出场顺序  —— 什么时候讲什么
叙述技法（本篇）：           每一步怎么讲    —— 场景、演算、试错、验证
```

叠加后的典型结构：

```
环 0  场景先行        ← 本篇 1.1
环 1  撞墙推演        ← 循环深入第一拍 + 本篇 1.3 逐轮演算
环 2  骨架 → 真实结构  ← 循环深入第二、三拍 + 本篇 1.5 代码配输出
环 3  试错与修正      ← 本篇 1.4
环 4  换角度验证      ← 本篇 1.6
```

> [!tip] 判据
> 写完通读一遍，问自己："读者会不会在某一轮演算里跟丢？"
> 会跟丢 → 补一张状态快照图，或把那一轮拆成两步写。
