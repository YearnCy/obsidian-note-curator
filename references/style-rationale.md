# 教学文风的设计依据

本文件记录 `note-style.md` 为什么采用当前规则。它不是写作时每次都要加载的操作手册，而是风格发生争议或需要继续迭代时的决策依据。

审阅日期：2026-09-17

## 一、参考范式与可迁移机制

| 范式 | 观察到的强项 | 本 skill 的采用方式 | 有意不照搬的部分 |
|---|---|---|---|
| [Fast DDS Simple App](https://fast-dds.docs.eprosima.com/en/v2.14.7/fastdds/getting_started/simple_app/simple_app.html) | 先展示最终目录与组件，再按依赖顺序搭建；每阶段都有构建或运行动作 | 教程使用“目标状态 → 最短路径 → 预期结果”；需要时区分手写 / 生成 / 配置文件 | 不重复贴完整文件；补上明确的失败信号和完整关键输出 |
| [Django Tutorial](https://docs.djangoproject.com/en/6.1/intro/tutorial01/) | 每个命令都有可核对结果，紧随“如果不符合预期先检查什么”；自然地指向下一篇 | 教程步骤固定写“目标 → 操作 → 预期 → 观察”，常见失败紧贴操作或集中在排错节 | 不把运行环境、版本差异和替代安装方案塞进主路径 |
| [Rust Book: Ownership](https://doc.rust-lang.org/book/ch04-01-what-is-ownership.html) | 先讲问题和坐标系，再立心智模型；以近似对照解释规则与例外；结尾留下下一问题 | 解释笔记使用“问题 → 模型 → 规则与对照 → 边界与例外 → 下一问” | 不为制造叙事而冗长铺陈；每个比喻只保留真正能承载推理的部分 |
| [Diátaxis Tutorials](https://diataxis.fr/tutorials/) 与 [Diátaxis](https://diataxis.fr/) | 明确区分 tutorial、how-to、explanation、reference 四类读者任务 | 每篇笔记以 `note_type` 声明主任务，并选择对应模板 | 不机械拆成四份文件；只要仍服务同一主任务，辅助内容可留在同篇 |

## 二、当前风格的核心判断

### 1. 教程不是解释的容器

教程的首要责任是让读者完成一条已验证路径。理论、变体和全量参数若放在每个操作前，会让第一次实践无法保持节奏。

因此：

- 主线只保留完成当前结果所必需的动作与最小理由
- 每步都必须产生或检查一个可观察信号
- 深解释移入“机制解释”小节或链接到 `explanation` 笔记
- 多方案、性能取舍和参数全集移入“变体与速查”或 `reference`

### 2. 解释不是定义列表

抽象概念若从术语定义开始，读者通常缺少判断它重要性的坐标。正确顺序是：旧问题或反直觉现象 → 心智模型 → 规则 → 只变一个变量的对照 → 例外的判据与限制。

因此：

- 首次定义必须回答“它解决什么”与“它不是什么”
- 例外必须给判断原则，不只罗列特殊名称
- 简化必须说明“忽略什么、为什么当前不影响结论、去哪里深入”
- 结尾要写可复述不变量和下一问，不写空泛“总结”

### 3. 验证是文风的一部分

“执行以下命令”不是教学闭环。可核对的输出、文件变化、日志字段和反向失败信号才让读者知道自己与作者处于同一状态。

因此：

- 命令和输出使用不同代码块
- 输出只保留稳定、关键的字段；版本与机器相关部分不伪造
- 没有出现成功信号时，给出第一个低成本检查点
- 涉及实测、源码和推断时标出事实来源与可信状态

## 三、长期一致性的红线

- 一个笔记只服务一个主读者任务
- 一个核心概念只使用一个稳定的术语和心智模型
- 教程的每个主步骤必须可验证
- 参数表不能吞掉因果叙事，叙事也不能淹没可查询事实
- 图只解决文字无法稳定表达的结构、时序、状态或层级
- 信息的不确定性通过来源、版本和 `status` 表达，而非把“是否来自对话”当作分类

## 四、后续迭代方法

不要因为某篇笔记“看起来不够丰富”就扩展规范。优先收集真实失败：

1. 读者在哪一步停住
2. 哪个术语在第一次出现时仍不可理解
3. 哪个输出无法用来判断成功
4. 哪个 MOC 顺序导致读者提前遇到高阶概念
5. 哪张表或图让主线变慢而非更清楚

修正规则时，先判断问题属于教程、操作指南、解释还是参考；不要用一种文体去修补所有类型。
