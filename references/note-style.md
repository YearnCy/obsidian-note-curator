# 笔记写作规范

目标：让三个月后的自己在脱离本次对话上下文后，仍能快速判断**这篇笔记解决什么问题、该从哪里开始、如何验证结果、卡住时看哪里**。

这不是把问答扩写得更长，而是把零散信息组织成可重复阅读、可执行、可维护的知识资产。

## 一、文风的设计原则

本规范吸收了四类高质量技术文档的共同机制，但不模仿任何品牌的句式：

| 来源范式 | 借用的机制 | 在本库中的落点 |
|---|---|---|
| Fast DDS Getting Started | 先展示目标产物，再按依赖顺序逐步搭建；每阶段都有可观察结果 | 教程笔记的“目标状态 → 最短路径 → 预期结果” |
| Django Tutorial | 每次操作紧跟可验证的输出、失败信号与下一步 | 每个操作单元必须写清“预期 / 不符合预期时先查什么” |
| Rust Book | 先给问题和心智模型，用对照案例解释规则与例外，再把下一节变成必要的答案 | 概念解释采用“问题 → 模型 → 对照 → 边界 → 下一问” |
| Diátaxis | 教程、操作指南、解释、参考分别服务不同读者任务 | 每篇笔记先声明主类型，避免正文在“教、讲、查、排错”之间来回跳 |

### 1. 一篇笔记只承担一个主读者任务

先判断读者打开笔记时最想完成什么，再选择 `note_type`：

| `note_type` | 读者任务 | 主写法 | 不要做什么 |
|---|---|---|---|
| `tutorial` | 第一次从零跑通一个完整闭环 | 小步操作、每步可见结果、少选项 | 在主线中讨论多个方案或堆大量参数 |
| `how-to` | 已有上下文，完成一个明确操作 | 直接步骤、前置状态、验收与回滚 | 从头讲完整理论史 |
| `explanation` | 理解机制、取舍或因果 | 模型、对照、规则、边界与推演 | 伪装成教程却没有可完成的产物 |
| `reference` | 快速查准确事实、接口或选项 | 稳定字段、表格、版本和来源 | 把检索表混进叙事主线 |

不要为了满足四种类型把一篇笔记拆成四个文件。只要某类内容仍服务同一个主任务，就放在同一篇的独立章节里：

- 教程末尾的一小段机制解释可以留在教程中，并链接到完整 `explanation` 笔记
- 教程所需的 5 个选项可以留在“速查”小节；当速查表已独立服务多篇笔记时，再拆成 `reference`
- 排错是教程或操作指南的闭环，不必单独建“排错笔记”；只有排错主题本身足够独立时才拆分

**判断标准：读者若只读主线，能否完成当前任务；读者若跳过主线，能否快速找到事实。两者都能，结构就合格。**

### 2. 叙事节奏：先让读者站稳，再解释为什么

- 教程先给出要完成的结果，再给最短路径；深解释放在成功之后或链接出去
- 概念解释先讲它解决的旧问题，再定义新概念；不要用定义开场把读者堵在门外
- **核心概念走三拍**：只讲痛点（不给名字）→ 给最小骨架 → 给真实源码与行号，详见 `spiral-teaching.md`
- **一般术语**首次出现时给一句可操作的定义，并在有独立笔记时挂 `[[wikilink]]`
- **禁止用尚未解释的概念去解释另一个概念**；本章用到的名词必须在前文或本节内就地解释过
- 每一节只引入完成本节所必需的新名词；写完一节自问“遮住后文，这一节能独立读懂吗”
- 使用一个稳定比喻帮助建立模型即可；不要为同一机制叠加多个比喻，也不要让比喻替代机制说明
- 规则之后立即给最小对照例子；例外在规则刚建立时说明其判据，不把例外藏到文末
- 章节结尾用一句不变量收束，并说明它解决了什么、下一步还缺什么

## 二、全库语言与格式基线

| 项目 | 约定 |
|---|---|
| 语言 | 中文叙述；术语首次出现写作 `device tree（设备树）`，后文择一稳定使用 |
| 语气 | 用短句说明因果和行动：先说明“为什么此时做”，再给“做什么”；避免“相关”“进行”“处理一下”等空泛词 |
| 视角 | 教程主线可用“我们”维持陪伴感；操作指南与参考优先用直接、客观的动词句 |
| 列表 | 用 `-` 起头，一条只表达一个判断或动作，句末不加句号 |
| 强调 | 命令、路径、文件名、宏、寄存器、函数名、固定输出一律用反引号 |
| 警示 | 已知风险用原生 `> [!warning]`；普通提醒写在紧邻动作的正文里，**不要把整句警示伪装成代码** |
| 代码块 | 必须标注语言；命令与其预期输出分开写；源码摘录必须写来源，见“代码与命令” |
| 表格 | 用于稳定、可扫描的信息（选项、对比、错误映射）；不要用表格承载连续因果推理 |
| 标题 | 全篇只有一个 H1；所有主章节使用 H2，如 `## 一、最短路径`；子节从 H3 起 |
| 编号 | 只有有先后依赖的章节使用 `一、二、三` 与 `2.1 / 2.1.1`；速查、FAQ、附录不编号 |
| 附件 | `<vault>/BaiduSyncdisk/pic/<笔记名>/`，用 `![[<笔记名>/<图名>.png]]` 嵌入；规则见第七节第 2 条 |
| 编码 | UTF-8、LF 换行 |

### 标题层级是结构，不是排版

正确层级：

```markdown
# Linux 驱动开发

## 一、前置条件

### 1.1 内核源码树

## 二、最短路径

### 2.1 编译模块

## 常用 API
```

- H1 只用于笔记标题，绝不重复使用
- `## 一、二、三` 是主线章节；其下用 `### 2.1`、`#### 2.1.1`
- `## 常用 API`、`## 术语表`、`## 附录` 是检索区，不强行编号
- 插入十进制小节时使用 `scripts/note.py insert --renumber` 或 `renumber`，不要手工改编号

## 三、教程笔记（`note_type: tutorial`）

教程是一条**已测试的学习路径**，不是完整知识百科。它的成功标准是：读者每做一步，都能看到承诺的结果，并知道下一步为什么合理。

### 1. 推荐骨架

```markdown
# <主题>

> [!abstract] 完成后你将得到什么
> <可观察的产物、行为或能力；写明适用版本/环境>

## 一、开始前

- 已具备：<前置条件>
- 先执行：<最小自检命令>
- 看到：<自检成功信号>

## 二、目标状态

<只在目录结构、组件边界或调用路径会影响理解时展示目标树/图>

## 三、最短路径

### 3.1 <第一个可见动作>

#### 目标
<本步只得到一个明确结果>

#### 操作
```bash
<命令>
```

#### 预期
```text
<关键输出或生成物>
```

#### 观察
- <读者应注意的变化，以及它说明了什么>

### 3.2 <下一步>

## 四、机制解释

<只解释主线中已出现、且不解释就无法迁移的问题>

## 五、变体与速查

<可选路径、参数表、版本差异；不打断最短路径>

## 六、常见失败

| 现象 | 先检查 | 原因 | 修复 |
|---|---|---|---|

## 七、下一步

- <更深的解释笔记>
- <相邻教程或官方资料>
```

不是每篇教程都需要七个章节：

- 不涉及文件与组件结构时，删除“目标状态”
- 没有稳定变体时，删除“变体与速查”
- 没有可预见失败时，删除“常见失败”
- **不得删除“开始前、最短路径、预期结果、下一步”这四个闭环要素**

### 2. 操作单元的硬规则

每一个主线步骤都按“目标 → 操作 → 预期 → 观察”写：

1. **目标**：只说本步完成什么，不说泛泛的学习目标
2. **操作**：一次只给一条主路径，命令可复制且变量有来源
3. **预期**：写关键输出、文件树变化、页面行为或可测信号，不写“应当成功”
4. **观察**：指出读者应该注意什么因果关系

可选项、替代工具、性能优化、平台差异不要插入主线。将它们收在“变体与速查”或链接到 `how-to` / `reference`。

### 3. 结果必须可核对

优先使用下列验收信号：

- 完整但短小的关键输出片段
- 明确的文件树或文件列表变化
- 可点击/可观测的 UI 行为
- 可复现的查询结果、返回码或日志标记
- 失败时的反向信号，例如“没有出现 `Publisher matched`，先检查订阅端是否启动”

不要承诺无法稳定复现的结果。若版本、硬件或网络会改变输出，明确写“关键字段应包含 ……”而非伪造完整日志。

## 四、概念解释笔记（`note_type: explanation`）

解释笔记的目标是让读者**想通**，而不是替读者跑完命令。

### 1. 推荐骨架

```markdown
# <概念或机制>

- 一句话结论：<可复述的不变量>

## 一、它要解决什么问题

<旧方案的痛点、约束或反直觉现象>

## 二、心智模型

<一张必要的图或一个稳定比喻；随后用文字把模型讲完整>

## 三、规则与对照

### 3.1 <规则>

<规则>

<近似但不同的两个例子，明确指出真正变化的变量>

## 四、边界与例外

- 例外成立的判据：<可判断的原则>
- 例外的限制：<不能做什么>
- 深入细节：[[相关参考笔记]]

## 五、把模型用回去

<用一两个真实场景推演模型如何指导选择>

## 六、下一问

- 现在已经能解释：<已解决的问题>
- 仍待回答：[[下一篇笔记]]
```

### 2. 解释时的写作顺序

- 先说明“为什么需要它”，再定义“它是什么”
- 先给读者熟悉的坐标系，再引入新模型
- 规则写成可复述的短句；紧跟最小、可运行或可验证的对照例子
- 允许为降低认知负担做简化，但要明确“这里暂时忽略什么、它为什么不影响当前结论、深入内容在哪里”
- 例外不要晚到：读者刚建立规则时，就给出判断例外的原则和限制
- 结尾不要空泛地写“总结”；写出一个不变量和一个由此必然出现的下一问题

## 五、操作指南与参考笔记

### 1. 操作指南（`note_type: how-to`）

面向已经知道背景、只想完成目标的读者。推荐骨架：

```markdown
# <在已知上下文中完成某操作>

- 适用：<明确起始状态、版本、权限或平台>
- 完成标准：<可验收结果>

## 步骤

1. <动作>
2. <动作>
3. <验证>

## 常见偏差

| 现象 | 原因 | 处理 |
|---|---|---|

## 原理与延伸

- 为什么这样做：[[机制解释]]
- 相邻操作：[[另一篇操作指南]]
```

- 先说起始状态，避免把隐含前提写进第 5 步
- 用一个首选做法，不在操作清单中展开方案评比
- 涉及不可逆、外部副作用或安全边界时，单独写风险与恢复路径

### 2. 参考笔记（`note_type: reference`）

面向查找，不承担首次教学。推荐内容：

- 版本、适用范围和权威来源
- 名称、字段、参数、默认值、单位、约束
- 可扫描的表格和最小示例
- 指向教程、操作指南、解释笔记的链接

参数细节、命令选项、寄存器位定义、API 签名应优先进入参考区。不要把连续教程正文切成“选项 A / B / C”的百科条目。

## 六、代码、命令与输出

### 1. 代码呈现：先整体，后局部

- 需要理解文件协作时，先展示目标目录树，并标明“手写 / 生成 / 配置”角色
- 先给一个可编译、可运行的完整最小文件；随后仅摘取需要解释的片段
- 不要把同一完整文件重复粘贴多次；重复说明时引用小节、行号、函数名或差异
- 函数摘录保留完整签名、形参和 `{}`；可省略函数体，但用注释说明省略的职责
- 每段源码在代码块正上方单独标注来源，路径使用项目根相对路径

````markdown
来源：`drivers/char/led_drv.c`

```c
static int led_open(struct inode *inode, struct file *filp)
{
    /* ... 省略：从 inode 解析设备私有数据 ... */
    return 0;
}
```
````

- 项目根不是当前工作区时，首次出现时写明项目根的逻辑名称；不写机器相关绝对路径
- 未阅读源码、无法确认的事实写 `> [!warning] 待核实`，并标注需要核对的文件或文档

### 2. 命令与预期输出必须分开

````markdown
执行：

```bash
python manage.py runserver
```

预期看到：

```text
Starting development server at http://127.0.0.1:8000/
```

若没有出现该行，先检查：`python -m django --version`
````

- 命令块只放命令，输出块只放关键输出
- 命令中的变量必须在同节或前文定义
- 多平台命令只有在实际验证过时才并列；否则给一个主平台路径，并把其他平台指向独立说明
- 魔法数字、版本钉死、等待时间等必须说明来源或原因；不确定时标注待核实

### 3. 命令族与速查表

正文讲“为什么用它、最小用法、选型边界”，稳定参数收进：

```markdown
#### 【命令名】相关用法

| 选项 | 描述 |
|---|---|
| `--flag` | <稳定含义与适用条件> |
```

表格不替代叙事。读者首次学习时走正文；需要回忆参数时查表格。

## 七、图、表、Callout 与来源

### 1. 图只解决空间或时间问题

- 只有文字难以说明“谁和谁交互、顺序是什么、状态如何迁移、层次如何包含”时才画 Mermaid
- 一张图只回答一个问题，放在解释它的段落附近；删图后正文仍应成立
- 调用链、核间交互、并发时序等代码讲解，先画图、编号，再按编号展开代码
- 目录树、内存布局、寄存器位段优先用文本树、ASCII 图或表格；不要为了“有图”而画图
- Mermaid 规则见 `references/diagrams.md`，Obsidian 扩展语法见 `references/obsidian-syntax.md`

### 2. 配图：目录约定与自动渲染

对话中产出的图（SVG / HTML 片段）本身只是文本，必须落成图片文件才能进笔记。不要手工截图，统一走脚本：

```bash
"$PY" "$SK/render_diagram.py" --note "MCU/xxx.md" --svg figs/a.svg --name "01-分层结构"
```

| 项 | 规则 |
|---|---|
| 位置 | `<vault>/BaiduSyncdisk/pic/<笔记名>/<图名>.png`；vault 无 `BaiduSyncdisk` 时退化为 `<vault>/pic/<笔记名>/` |
| 子目录名 | 与笔记文件名一致（不含 `.md`） |
| 图名 | `NN-描述性中文名`，`NN` 是图在正文中的出现顺序，如 `01-四个指针.png` |
| 嵌入语法 | `![[<笔记名>/<图名>.png]]`；沙箱内用 `--format svg` 出图时写 `![[<笔记名>/<图名>.svg\|宽]]` |
| 底色 | 默认 `#2b2b2b`（与 Obsidian 深色主题一致），可用 `--bg` 覆盖 |
| 分辨率 | 默认 `--scale 2` 输出 2 倍图，缩放后不糊 |

渲染器用本机 Edge / Chrome 的无头模式，**不依赖** ImageMagick / Inkscape / Playwright / cairosvg。DSH 沙箱内浏览器通常起不来，改用 `--format svg`（Obsidian 原生渲染），细节见 `env-notes.md` 第五节。

- 输入 SVG：尺寸自动取 `viewBox`
- 输入 HTML：给的是**片段**（不含 `<html>/<body>`），脚本负责包骨架；尺寸优先 `--width/--height`，其次读片段里的 `data-w` / `data-h`
- 批量：`--manifest figs.json`，一次出全套

> [!warning] 图下必须有说明
> 每张图后面写 1~2 句它体现了什么。手机上放大看不清细节时，文字是唯一退路。

图该画什么、用哪种形式（状态快照 / 并列对比 / 结构分层），见 `narrative-style.md` 第二节；Mermaid 语法见 `diagrams.md`。

### 3. Callout 只表达语义，不充当装饰

```markdown
> [!note] 背景补充
> 主线暂时不展开的必要背景

> [!tip] 经验
> 已验证的捷径、观察技巧或维护习惯

> [!warning] 风险
> 已知危险操作、版本陷阱或可能造成损失的条件

> [!warning] 待核实
> 暂无法由现有源码、日志或官方资料确认的推断；说明核对目标

> [!question] 待办
> 当前笔记暴露但未解决的问题；能转为任务时优先转为任务
```

不要用 `note` 来区分“用户原话”和“整理补充”。知识的可信度应由**来源和状态**表达，而不是由内容来自哪一轮对话表达。

### 4. 来源与事实边界

- 一篇笔记开头可列主要资料来源，但关键事实、代码片段、版本行为仍需就近标出来源
- 官方文档、源码、实测日志、个人推断要可区分
- 以“已验证 / 待核实 / 版本相关”描述事实状态，不把不确定内容写成结论
- 外部链接用于权威原文；库内概念、教程和参考统一使用 `[[wikilink]]`

## 八、Frontmatter 与长期维护

新建笔记使用下列最小元数据；老笔记只在本次编辑确有需要时补齐，不强制全库迁移：

```yaml
---
note_type: tutorial
status: draft
tags:
  - Linux/驱动
aliases: []
keywords:
  - rpmsg
updated: 2026-09-17
moc: "[[Linux内核 MOC]]"
related: []
---
```

| 字段 | 说明 |
|---|---|

## 九、拆分、链接与阅读路径

- 一篇笔记只讲一个可独立完成的知识单元；当第二个单元可以被其他笔记独立引用时，考虑拆分
- 教程的“下一步”链接到难度自然上升的下一篇；解释笔记的“下一问”链接到当前模型解决不了的问题
- 同层并列的实现方案要互链“对比”，上下游概念要在 MOC 阅读路径中排序
- MOC 只管理阅读路径、分支地图和维护状态；多维筛选交给 `.base`，详见 `moc-system.md`
- 不以行数作为唯一拆分依据：超过 400 行是复查信号，不是机械拆分命令

## 十、落盘前检查清单

- [ ] 已选择 `note_type`，读者打开它的主任务明确
- [ ] 标题层级只有一个 H1，主章节从 H2 开始
- [ ] 教程每个主线步骤都有可观察的预期结果
- [ ] 解释笔记先建立问题和模型，再给规则与例外
- [ ] 命令、预期输出、源码来源没有混在同一个代码块里
- [ ] 可选分支、速查和深解释没有打断最短路径
- [ ] 核心概念走完三拍（痛点 → 骨架 → 真实来源），没有只给一句定义就往下走
- [ ] 已跑 `step_audit.py`，并逐条确认每个术语的首次出现处读者能看懂
- [ ] 新术语首次出现已定义，已有独立笔记已挂 wikilink
- [ ] 事实的来源、版本或待核实状态足够清楚
- [ ] 图只在解决结构/时序问题时出现，并已在 Obsidian 中验证渲染
- [ ] 图已用 `render_diagram.py` 落进 `pic/<笔记名>/`，嵌入语法为 `![[<笔记名>/<图名>.png]]`（或 `--format svg` 的 `.svg`），图下有说明
- [ ] 已先执行 `--dry-run`，实际检查 diff；正式写入会创建可恢复备份

## 十一、禁止事项

- 禁止删除或压缩用户已有叙述，除非用户明确要求重写；整理默认只做增补、重排和链接
- 禁止用尚未解释的概念去解释另一个概念；教学类笔记禁止把台阶留到用户追问时再补
- 禁止把用户惯用术语强行改写为“更规范”的说法
- 禁止编造源码、寄存器地址、命令输出、版本兼容性或测试结果
- 禁止为了看起来完整而强行凑七章、强行画图、强行加入多个替代方案
- 禁止把未验证的推断写成确定结论；标为待核实并说明核对方向
- 禁止一次整理跨越超过 3 篇笔记；跨度更大时先处理主线，其余转为明确待办
