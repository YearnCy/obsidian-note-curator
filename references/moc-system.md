# MOC 索引与子笔记组织规则

采用三层结构：**全库总索引 → 主题 MOC → 子笔记**。

```
<仓库根>/
├── 全库总索引 MOC.md          ← L0：唯一入口，列出所有主题
├── Linux内核/                 ← 主题目录
│   ├── Linux内核 MOC.md       ← L1：该主题的导读路径
│   ├── 字符设备驱动框架.md     ← L2
│   ├── GPIO 子系统.md
│   └── Linux内核 MOC.assets/
├── 嵌入式开发/
│   ├── 嵌入式开发 MOC.md
│   └── ...
└── Linux驱动.md               ← 迁移完成前，未整理的历史笔记原地保留
```

---

## 一、各层的职责

### L0 全库总索引 MOC（根目录，全库唯一）

只做一件事：把人送到正确的主题。内容不超过一屏。

```markdown
# 全库总索引

## 主题
- [[Linux内核 MOC]] — 内核与驱动：字符设备、GPIO、pinctrl、irqchip、设备树
- [[嵌入式开发 MOC]] — 从零开始的嵌入式：工具链、调试接口、RTOS
- [[SemiDrive X9 MOC]] — X9 平台 bring-up、R5 与 Linux 的 rpmsg 通信

## 未归类的历史笔记
- [[Linux驱动]] — 待拆分（当前 400+ 行，含 sparse/smatch/字符设备/API 速查）
- [[Kernel6.1阅读笔记]] — 待归类

## 维护
- 上次断链检查：2026-09-03
```

### L1 主题 MOC（每个主题目录一个）

核心是**「阅读路径」**——一个有序列表，按从浅入深排好，读一遍就等于学完这个主题。骨架见 `assets/templates/topic-moc.md`。

```markdown
# Linux内核 MOC

## 阅读路径（按顺序）
1. [[内核模块基础]] — 模块的编译、加载、卸载，先能跑起来
2. [[字符设备驱动框架]] — file_operations、注册与注销、设备号
3. [[GPIO 子系统]] — gpiod 接口、设备树绑定、与 pinctrl 的关系
4. [[中断与 irqchip]] — 中断号映射、上半部/下半部
5. [[并发与同步]] — spinlock、mutex、atomic 的选型

## 分支地图
- 调试
  - [[KGDB_WSL_调试配置指南]]
  - [[内核oops定位]]
- 工具链
  - [[sparse 与 smatch]]

## 状态
- [ ] [[pinctrl 子系统]] 待创建（GPIO MOC 里已有多处引用）
- [ ] [[Linux驱动]] 的第 3~5 章待拆到这里
```

### L2 子笔记（主题目录下）

一篇子笔记只讲**一个可独立完成的知识单元**。先按 `references/note-style.md` 标记其 `note_type`：

- `tutorial`：第一次从零跑通一个完整闭环
- `how-to`：在既定上下文中完成一个明确操作
- `explanation`：理解机制、取舍或因果
- `reference`：查接口、参数、版本和稳定事实

阅读路径的默认顺序是：公共解释 / 前置教程 → 主教程 → 进阶操作 → 参考资料。不是每种类型都要出现；顺序以理解依赖为准。

### MOC 与 Bases 的分工

MOC 和 `.base` 不是彼此替代：

| 工具 | 负责什么 | 不负责什么 |
|---|---|---|
| MOC | 有序阅读路径、分支地图、学习顺序、下一步 | 复杂筛选、动态统计、状态聚合 |
| Base | 按 `note_type`、`status`、tag、日期等元数据做多维筛选和表格/卡片视图 | 叙事、解释为什么这个顺序适合学习 |

只有出现真实的筛选需求时才新建 `.base`。推荐的第一个视图是“待维护笔记”：筛选 `status != "reviewed"` 或 `status == "needs-verify"`。不要为了使用 Bases 把手工阅读路径替换成没有顺序感的数据库表。

## 二、粒度判断：什么时候拆分

命中任一条件就拆：

| 条件 | 阈值 |
|---|---|
| 行数 | 单篇 > 400 行（触发复查，不是机械拆分） |
| 顶层章节 | `一、二、三…` 超过 7 个 |
| 主题纯度 | 出现「常用API」「速查表」「附录」之类明显不同性质的大块 |
| 复用需求 | 有 2 篇以上其他笔记需要引用其中的某一节 |

拆分时的动作顺序：

1. 新建子笔记，把原章节内容整体搬过去（用 `note.py replace` 保留原标题并留下指向新笔记的链接）。
2. 原位置**不删除内容**，改为一段摘要 + `→ 详见 [[新笔记]]`。
3. 在主题 MOC 的阅读路径里插入新条目。
4. 拆分动作会改变笔记间的引用关系，**必须**跑一次断链检查。

## 三、链接策略

### 必建的链接

- 每篇 L2 子笔记 → 其 L1 主题 MOC（frontmatter 的 `moc` 字段 + 正文底部的收尾章节）
- 阅读路径上相邻的笔记 → 互相链接（前一篇底部写「下一步：[[下一篇]]」）
- 正文中提到的、已有独立笔记的概念 → 直接 `[[wikilink]]`

### 链接写法

```markdown
[[GPIO 子系统]]                      普通链接
[[GPIO 子系统|GPIO 子系统详解]]       带显示文字
[[GPIO 子系统#2.1 gpiod 接口]]       指向具体章节
![[架构图.png]]                      嵌入附件
```

正文中第一次提到某个有独立笔记的概念时加链接，同一篇里重复出现不必反复加。

### 反向导航

每篇子笔记底部必须有收尾章节，且**必须包含「所属主题」**。章节名按 `note_type` 取对应模板的收尾，不要四种类型都套同一个名字：

| 类型 | 收尾章节 | 模板 |
|---|---|---|
| `tutorial` | `## 下一步` | `assets/templates/sub-note.md` |
| `explanation` | `## 下一问` | `assets/templates/explanation-note.md` |
| `how-to` | `## 原理与延伸` | `assets/templates/how-to-note.md` |
| `reference` | `## 从哪里开始` | `assets/templates/reference-note.md` |

```markdown
## 下一步
- 上一步：[[字符设备驱动框架]]
- 下一步：[[中断与 irqchip]]
- 所属主题：[[Linux内核 MOC]]
```

## 四、MOC 的维护纪律

1. **阅读路径的顺序是资产。** 顺序错了，MOC 就退化成标签页。每次新增子笔记都要重新确认插入位置。
2. MOC 里出现 `[[断链]]` 是明确的信号：要么这篇笔记还没建，要么建了没挂进来。用「状态」章节显式记下来。
3. 不要在 MOC 里写实质内容。MOC 只有路径、地图、状态三样东西。
4. 每次整理结束后，更新 MOC 的 `updated` 与「上次断链检查」日期。
5. `vault.py audit` 报出“声明了 `moc` 但不在阅读路径”时，先判断该笔记是否真的属于线性学习路径；旁支、索引或仅供检索的参考笔记可以不进入路径，但应在分支地图或 `related` 中可达。

## 五、历史笔记的迁移策略

很多库是从 Typora / 其他工具迁移来的，常见状态是一堆扁平的历史笔记、彼此零 wikilink。
**不要一次性全量重构**，采用「碰到谁迁移谁」：

| 触发 | 动作 |
|---|---|
| 用户提问涉及某篇历史笔记 | 就地补充内容；若该笔记达到拆分阈值，就地拆出子笔记到新建的主题目录 |
| 同一主题下已积累 3 篇以上子笔记 | 补建该主题的 MOC |
| 主题数达到 3 个 | 补建全库总索引 MOC |

这样 MOC 结构是被真实需求推着长出来的，而不是预先设计好的空架子。
