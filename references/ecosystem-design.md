# Skill 生态设计与能力边界

`obsidian-note-curator` 的价值不是覆盖所有 Obsidian 功能，而是成为“知识质量的编排层”。本文件固定各能力的职责边界，防止 skill 越做越像不稳定的大杂烩。

## 一、三层架构

```text
读者与知识层
  note-type、教学文风、概念依赖、MOC 阅读路径、来源与可信状态
  └─ obsidian-note-curator 的核心职责

确定性操作层
  vault.py 扫描与 audit、note.py dry-run/写入/备份、ob.py 官方 CLI 适配
  └─ 只提供事实、诊断与可恢复的执行

可选集成层
  官方 Obsidian CLI、Bases、TaskNotes、Kanban/Dataview、外部同步服务
  └─ 只有用户已采用且明确需要时才接入
```

### 核心不变量

1. Markdown 笔记是唯一知识源；任何视图、任务或同步层都是派生能力
2. 没有 Obsidian 正在运行、没有插件、没有网络时，定位、写作、链接审计仍可完成
3. 自动化默认只报告问题，不默默重排 MOC、不创建任务、不改写历史笔记
4. 每次正式写入都先可预览，并保留可恢复的原文件副本
5. 读者任务（`note_type`）与事实状态（`status`）是正交的：教程也可以 `needs-verify`，参考也可以 `draft`

## 二、职责矩阵

| 需求 | 首选能力 | curator 介入点 | 不应做什么 |
|---|---|---|---|
| 整理对话为可学习笔记 | curator + note.py | 判断类型、补台阶、写作、链接、验证 | 只把聊天记录全文复制进去 |
| 查断链、孤儿、待核实、MOC 漏项 | vault.py audit | 解释报告、形成复查队列 | 自动删除孤儿或强塞进 MOC |
| 安全移动 / 重命名笔记 | 官方 Obsidian CLI（`obsidian-cli` / `obsidian-cli-official` 提供命令参考） | 先判断迁移是否合理，再验证链接 | CLI 不可用时直接文件移动 |
| 多维筛选待维护笔记 | `obsidian-bases`（Bases） | 设计元数据（`note_type` / `status`）和视图意图 | 用 Base 替代学习顺序 |
| Obsidian 语法细节 | `obsidian-markdown` | 只保留写笔记会用到的语法基线 | 把扩展语法百科搬进 curator |
| CLI 全量命令、脚本化操作 | `obsidian-cli` / `obsidian-cli-official` | 用 `ob.py` 封装必要子命令 | 在 curator 里复刻整本 CLI 手册 |
| 追踪有责任人的实际工作 | 已有任务系统 | 将有验收的承诺回链到知识上下文 | 自动把每条知识缺口转为任务 |
| 插件开发 | 专门的 plugin-dev skill | 仅提供内容模型或笔记规范 | 把插件源码维护塞进 curator |
| 跨系统同步 | 专门的 sync skill | 保持 Markdown 作为源 | 在 curator 内置长期运行服务 |

> **DSH 环境提示**：上表中的 `obsidian-markdown` / `obsidian-bases` / `obsidian-cli` /
> `obsidian-tasks` 等兄弟 skill 在 DSH 里通常并未安装。此时由「curator 介入点」一列自行兜底：
> 语法基线用本 skill 的 `obsidian-syntax.md`，CLI 用 `ob.py`，Bases 与任务系统在用户确认
> 已采用之前一律不假设存在。

## 三、功能准入检查

新增能力前逐项回答：

1. 它是否直接改善“读者理解、知识可信度或长期可维护性”之一？
2. 它能否在纯本地 Markdown 模式下优雅降级？
3. 它是否重复了已安装 skill 的明确职责？
4. 它的输出是否可审查、可回滚、可解释？
5. 它是否会诱发未授权的外部副作用、插件依赖或噪声任务？

任一答案不理想时，优先写一份集成说明或调用边界，而不是把能力硬塞进脚本。

## 四、已采用的设计

| 设计 | 为什么保留 |
|---|---|
| `note_type` + 四类模板 | 让写作方式匹配读者目标，避免教程、解释、参考混为一谈 |
| `status` + `audit` | 将“待核实、草稿、已复核”变成可复查的维护状态，而不是藏在正文 |
| MOC 与 Bases 分工 | 同时保留叙事顺序与多维检索，不让任一工具越权 |
| 默认备份 + dry-run | 让编辑过程可预览、可恢复，符合已有 Git 同步场景 |
| 官方 CLI 可选增强 | 移动/重命名有链接感知，同时不让 GUI 依赖阻断基本工作流 |
| Mermaid 节点 `internal-link` 可点击 | Obsidian 官方原生支持；节点名与笔记名一致时可省一次跳转，但必须有正文 `[[wikilink]]` 作为稳定入口 |
| 任务渐进出口 | 让行动承诺可被追踪，又不把知识库变成待办垃圾场 |

## 五、明确延后或拒绝的设计

| 设计 | 原因 | 可重新考虑的条件 |
|---|---|---|
| 自动每周改写 MOC / 自动拆分长笔记 | “长”或“未入路径”不等于错误，自动变更会破坏作者的叙事意图 | 有足够真实复查样本，并由用户批准具体规则 |
| 自动创建任务 | 容易把知识缺口误变成行动承诺，造成任务噪声 | 用户已有稳定任务规范并请求自动化 |
| 内置本体抽取与定时同步 | 与现有 ontology-sync 职责重复，且会引入领域模型和长期运行依赖 | 用户明确采用统一实体模型并授权接入 |
| 自动安装 / 启用 Obsidian 插件 | 改变用户桌面环境，不是知识整理必要条件 | 用户明确选择插件和目标配置 |
| 自动清理备份 | 备份删除本身有数据丢失风险 | 用户给出保留策略和明确确认 |

## 六、推荐的成长路径

1. 先在真实笔记中使用四类模板，观察读者停顿与复查成本
2. 用 `audit` 建立问题基线，不急于加定时任务
3. 当“按状态 / 类型筛选”成为重复动作时，再创建一个最小 Base
4. 当存在明确负责人和期限时，再与既有任务系统建立适配
5. 当用户反复执行同一审计或迁移动作时，再讨论一次性或周期自动化

这条路径让生态随真实使用生长，而不是为未来假设预装复杂度。
