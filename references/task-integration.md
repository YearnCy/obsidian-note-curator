# 待办与任务系统的渐进式集成

笔记中的“待办”有两种完全不同的含义，不能混在一起：

| 类型 | 例子 | 默认落点 |
|---|---|---|
| 知识缺口 | “需要核对某寄存器位的源码定义” | 笔记中的 `> [!question] 待办` + `status: needs-verify` |
| 可执行承诺 | “下周补一张测试波形并复测” | 任务系统中的独立任务，笔记保留链接 |

## 一、默认策略：不强依赖任何任务插件

`obsidian-note-curator` 的核心职责是维护知识质量，不应因为没有 Kanban、Dataview 或 TaskNotes 插件而失效。

- 未检测到任务系统：保留 `> [!question] 待办`，并在 frontmatter 设 `status: needs-verify`（如确有未验证事实）
- 使用 `scripts/vault.py audit` 汇总 `待核实` 和 `待办`，形成可复查清单
- 不自动把每个知识缺口创建成任务，避免产生噪音和重复追踪

## 二、出现既有任务系统时的可选出口

只有满足以下所有条件才建议建立任务：

1. 用户明确要求跟踪，或待办有责任人、截止时间、外部行动或可验收产物
2. 当前 vault 已存在一个明确的任务约定：`Tasks/`、TaskNotes 插件、或用户指定的任务目录
3. 可确定目标系统的字段与状态，不靠猜测创建
4. 新任务能回链到原笔记，避免任务与知识上下文脱节

推荐格式：

```markdown
- [ ] 核对 `drivers/foo/bar.c` 中寄存器位定义
  - 来源：[[GPIO 子系统#四、待核实事项]]
  - 完成标准：补充源码行号与适用 SoC 版本
```

## 三、与已安装 skill 的边界

- 使用 `obsidian-tasks` 时：由它维护 Kanban、任务 frontmatter 与 Dataview 面板
- 使用 TaskNotes 时：由 `obsidian-plugin-tasknotes` 管理 API 增删改查
- DSH 里这两个 skill 通常并未安装：未安装时一律退回第一节的默认策略（`> [!question] 待办`
  + `status: needs-verify`），不要因为缺少插件而跳过知识缺口记录
- 本 skill 只负责：判断待办是否值得外化、提供来源链接、在笔记中把事实状态标清
- 不自动安装或启用插件，不修改用户现有的状态命名和任务目录

## 四、闭环规则

任务完成后，不只把任务标记完成：

1. 回到原笔记补入验证证据、来源或结论
2. 移除或更新对应 `待核实` / `待办` callout
3. 更新 `updated` 与 `status`
4. 运行 `vault.py audit` 确认待核实项确实消失
