# 循环深入：面向新手的教学铺台阶

- **一句话**：任何复杂概念都不该"先定义再用"，而应"先撞墙、再给形、最后给实"；同一个概念在文中登场 2~3 次，每次只多讲一层。
- **适用**：`note_type` 为 `tutorial` 或 `explanation`，且读者对该主题不熟（默认情形）。
- **不适用**：`reference`（速查）、`how-to`（读者已有上下文）。

## 一、问题：线性写作必然留坑

线性写作的通病是**用一个尚未解释的概念去解释另一个概念**。真实反例（`D:\mycode\net\tutnet.c:114`）：

```c
/*
 * 为什么不是「一个 sk_buff 队列」而是「一段裸内存 + 长度」？
 *   因为硬件收到帧时并不知道 sk_buff 是什么，它只会往一块物理内存里 DMA 写字节……
 */
struct tutnet_rx_slot {
        u16     len;
        u8      data[TUTNET_MAX_FRAME];
};
```

这段注释写得很好，但它**假设读者已经知道 `sk_buff` 是什么**。而在它之前，`sk_buff` 只在文件头的通路图里出现过名字，从未被解释。读者到这里必然卡住：不知道 `sk_buff`，就无法理解"sk_buff 队列"，更谈不上理解"为什么不这么做"。

作者本人的困惑很典型：

> 为什么不是「一个 sk_buff 队列」而是「一段裸内存 + 长度」？**在这段话之前完全没有 sk_buff 形式的介绍，下面的代码也有这样的问题。**

同类失败模式：

| 模式 | 表现 | 为什么读者会卡 |
|---|---|---|
| 用未定义概念解释另一概念 | "为什么不用 X 队列"——X 没介绍过 | 无法评估这个取舍 |
| 只给一句定义就往下走 | "`sk_buff` 是套接字缓冲区" | 知道名字，不知道它解决什么问题，读不出字段的必然性 |
| 只给真实结构不给骨架 | 直接贴 60 个字段 + 条件编译 | 淹没在细节里，抓不住主线 |
| 用"众所周知"跳过 | "显然，tag 就是名额" | 比喻替代了机制，遇到边界就崩 |

## 二、模型：A→B→C 不是顺序，是螺旋

要讲清楚概念 A，必须先讲 B；要讲 B，必须先讲 C。

线性写作会这样做（错误）：

```
C → B → A       每个只讲一遍，讲 A 时 B 已经模糊了
```

螺旋写作应该是（正确）：

```
简 C  →  简 B  →  深 A  →  深 B  →  深 C
 ↑                                    ↓
 └────────── 每次只加深一层 ──────────┘
```

判据：

- **简 C 时不用 B 和 A 的任何知识**。C 必须能被"只知道起点契约"的读者独立看懂。
- **深 A 时，B 和 C 的简版已经在读者手里**，可以直接引用"前面说的那个 X"。
- **深 B、深 C 放在最后**，此时读者已经通过 A 的实战理解了 B、C 为什么存在，细节才落得下去。

> [!warning] 常见误判
> "我在开头加了个术语表"不等于铺了台阶。
> 术语表给的是**定义**，台阶给的是**动机**。读者需要的是"不这么做会撞什么墙"，不是"这个词是什么意思"。

## 三、三拍：每个核心概念登场三次

不是每个名词都要三拍。**核心概念**（驱动整个机制的结构体、机制、模式）才需要。判断标准：如果删掉它，全文主线就断了，那它是核心概念。

### 3.1 拍 1：只讲痛点，不给名字

先演一个"朴素做法撞墙"的过程，**不出现这个概念的名字**。让读者自己感到"这里缺个东西"。

写法示例（讲 `sk_buff` 之前）：

```
如果包就是"一块内存 + 长度"，加一个 IP 头只有一个办法：
把 1500 字节整体往后挪 20 字节。
一个包走完三层要挪 3 次，每次都是全量 memcpy。

需求 1：必须能在不移动数据的前提下，往头尾长出空间。
需求 2：一批元信息要跟着数据走，不能靠参数列表。
需求 3：一份数据可能被多方同时持有。
```

到这里读者只知道"需要个对象"，不知道它叫什么。这时才可以说：

> 这三条需求，就是后面那个核心结构体的全部设计动机。它叫 `sk_buff`。

### 3.2 拍 2：给最小骨架

给一个**裁剪到只剩必要字段**的结构/代码。每个字段后面跟"它被什么逼出来的"。

```c
/* 第一版：只满足需求 1 */
struct sk_buff_min {
        unsigned int    len;
        unsigned char  *head, *data, *tail, *end;   /* data/tail 会动 */
};
```

要点：

- 字段数控制在 4~8 个
- **只保留与当前需求直接相关的**，其余全部省略并注明"后面会加"
- 每加一批字段，说明是满足了哪个新需求

### 3.3 拍 3：给真实来源

此时才贴真实结构，并给出行号与裁剪说明：

```c
/* include/linux/skbuff.h:856 起，去掉 union 和条件编译 */
struct sk_buff {
        char             cb[48] __aligned(8);        /* :892 */
        unsigned int     len, data_len;              /* :908 */
        ...
};
```

必须做到：

- 写明文件路径与起始行号
- 说明裁剪了什么（"去掉 union 和条件编译"），否则读者以为真实结构就这么点
- 关键字段补行号，方便跳转核对

### 3.4 三拍对照表

| 拍 | 读者状态 | 内容形态 | 禁止 |
|---|---|---|---|
| 1 痛点 | "我需要个东西" | 场景推演、撞墙、需求清单 | 出现该概念的名字 |
| 2 骨架 | "它大概长这样" | 4~8 字段的最小结构 | 贴完整真实结构 |
| 3 真实 | "原来内核里是这样" | 真实源码 + 行号 + 裁剪说明 | 不给行号或不说裁剪了什么 |

## 四、读者起点契约

不知道读者懂什么，就无法判断"什么算未解释"。所以教学笔记**开头必须声明起点**：

```markdown
> [!info] 读者起点
> 假设你会：C 语法、`module_init` / `module_exit`、基本 `struct` 用法。
> 本文从零讲：`blk-mq`、tag、request、hctx —— 不需要任何前置。
```

作用有三：

1. **定义判据**：不在"会"列表里的名词，第一次出现必须有铺垫
2. **防止过度铺垫**：已经声明的起点不必再解释，避免啰嗦
3. **可复用**：同一主题的系列笔记可以共享同一份起点契约

> [!tip] 起点写窄不写宽
> 宁可把起点写得窄（假设读者懂得少），也不要写宽。写宽了会出现"读者卡住但作者以为他懂"的盲区。
> 唯一例外：读者明确说明已具备某背景（例如"我在写 XMC4700 驱动"），此时可把对应领域列为已会。

## 五、概念登记表

写作过程中维护一张表（不必写进笔记，工作草稿即可）：

| 概念 | 首拍（痛点） | 二拍（骨架） | 三拍（真实） | 状态 |
|---|---|---|---|---|
| `sk_buff` | 环 1.5 三条需求 | 环 2.1-2.3 三版骨架 | 环 2.4 真实结构 | ✅ |
| `net_device` | 环 4.1 一个网卡要记什么 | 环 4.2 ops 表 | 环 4.4 真实字段 | ✅ |
| `napi_struct` | 环 5.1-5.3 中断困境 | 环 5.4 五字段 | 环 5.4 真实定义 | ⚠️ 三拍合并了 |

表的作用是暴露**漏拍**：某个概念只有二拍没有一拍，说明读者不知道为什么需要它；只有一拍没有三拍，说明读者只得到比喻没得到事实。

## 六、交付前审计

### 6.1 机械审计：`scripts/step_audit.py`

```bash
"$PY" "$SK/step_audit.py" --file "网络设备运行机制.md"
```

脚本扫描全文，按 H2 章节分组列出**每个技术标识符的首次出现位置**，输出一张待审查清单。它不做判断（不猜"算不算解释过"），只把需要人眼过一遍的位置摊出来。

输出示例：

```
第一章  从一条命令说起
  行  33  sk_buff               ← 本章首次引入
  行  36  napi_poll             ← 本章首次引入
第二章  最朴素的设计
  行  78  request               ← 本章首次引入
```

审查方法：对清单里每一条，回到该行问一句——

> **读者读到这里时，认识这个词吗？**

- 认识（前文铺过）→ 通过
- 不认识但本行就打比方讲清了 → 通过（相当于"就地一拍"）
- 不认识且直接拿来解释别的 → **必须改写**

### 6.2 人工三检查

**检查 A：倒读法。** 从最后一节往回读，每遇到一个"为什么 X"的句子，暂停，问"这句话里的名词，前面的章节解释过吗"。倒读能有效暴露正向阅读时的"顺畅错觉"。

**检查 B：删后读前。** 把第 N 节之后的内容全部删掉（心里删即可），只读前 N 节。如果前 N 节无法独立读懂，说明它依赖了后文——顺时针依赖，必须调整顺序。

**检查 C：起点回看。** 回到开头的"读者起点契约"，逐条核对：契约说"从零讲"的概念，是否真的有一拍？

## 七、禁止模式（反例库）

### 7.1 用未定义概念解释另一概念

```markdown
❌ 为什么不是「一个 sk_buff 队列」而是「一段裸内存 + 长度」？
   （sk_buff 在此前从未被解释）
```

正确展开顺序：

```markdown
✅ 1. 先讲：包在协议栈里要经过多层，每层都要加头
   2. 再讲：如果只有"一块内存+长度"，加头就要整体拷贝
   3. 再讲：所以需要"可移动的数据边界指针"
   4. 再讲：这个想法 + 元信息 + 引用计数 = sk_buff
   5. 才可以问：为什么硬件那层不用 sk_buff
```

### 7.2 只给一句定义就往下走

```markdown
❌ `sk_buff` 是 Linux 网络栈中表示数据包的结构体。
   （读者知道了名字，但不知道它为什么存在，后面讲 char/data/tail/end 时无法理解为何要这么多指针）
```

```markdown
✅ 先演"加头要整体拷贝"的痛点 → 再给四个指针 → 此时读者自己就能说出"为什么要两个边界指针"
```

### 7.3 只给真实结构不给骨架

```markdown
❌ 直接贴 `struct net_device` 的 200 行定义
```

```markdown
✅ 先给"一个网卡要记什么"的朴素版本（名字/MAC/MTU/统计）→ 再给"内核要调你干活所以需要函数表" → 再给真实结构的关键 12 个字段
```

### 7.4 用比喻替代机制

```markdown
❌ tag 就像停车场的车位，很好理解。
   （比喻给了直觉，但读者不知道"满了会怎样""谁负责归还""编号用来干什么"）
```

```markdown
✅ 比喻只用一句建立初始印象，紧接着给机制：谁分配、何时归还、满了谁等、编号的最终用途（数组下标）
```

## 八、与其他文风规则的关系

- **文风基线**（`note-style.md`）管的是句子怎么写；本文管的是**内容按什么顺序出现**。两者不冲突：先定顺序，再定句式。
- **MOC 阅读路径**管的是"多篇之间"的顺序；本文管的是"一篇之内"的顺序。两者判据一致：只能依赖已经解释过的东西。
- **`[[wikilink]]` 不能替代台阶**。链接只解决"这个概念另有详解"，不解决"读者此刻没有能力理解这句话"。要么就地给一拍，要么把这句话挪到后面。
